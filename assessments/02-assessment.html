Assessment 3

Capstone Project - 30%

Author

Mr. John Jennings

Capstone Project

The capstone project in the AWS Academy Cloud Architecting (ACA) curriculum is designed as the culminating experience that allows learners to demonstrate their mastery of AWS cloud concepts, architecture best practices, and hands-on implementation. It integrates knowledge gained from the entire course, covering topics such as networking, compute, storage, databases, security, monitoring, and automation.

In the capstone, students are typically presented with a real-world business problem that requires designing and deploying a secure, scalable, and cost-effective cloud solution. They must apply the AWS Well-Architected Framework, considering the five pillars: operational excellence, security, reliability, performance efficiency, and cost optimization. Learners design architecture diagrams, justify technology choices, and implement core services like Amazon EC2, S3, RDS, IAM, VPC, and CloudFormation for infrastructure as code.

The project emphasizes not only technical accuracy but also professional skills such as documentation, communication, and solution presentation. By completing the capstone, participants demonstrate their ability to translate business requirements into a working AWS architecture. This project is also an opportunity to build a portfolio piece, showcasing readiness for cloud-related roles. Ultimately, it reinforces problem-solving, critical thinking, and applied cloud architecture skills in a practical context.

Once given the assessment brief, you will be required to prepare an architectural diagram solution to the problem and then over 2 weeks you will have the opportunity to create and deploy your solution architecture to AWS.

This project is worth 30% of your module grade.

Overview and objectives

Throughout this course, you have completed hands-on labs. You have used different AWS services and features to create compute instances, install operating systems (OSs) and software, deploy code, and secure resources. You practiced how to enable load balancing and automatic scaling and how to architect for high availability to build lab-specific applications.

In this project, you’re challenged to use familiar AWS services to build a solution without step-by-step guidance. Specific sections of the assignment are meant to challenge you on skills that you have acquired throughout the Academy Cloud Architecting (ACA) course.

By the end of this project, you should be able to apply the architectural design principles that you learned in this course to do the following:

  • Create a database (DB) instance that the PHP application can query.

  • Create and deploy the highly available PHP application with the load distributed across multiple web servers and Availability Zones.

  • Use AWS Secrets Manager.

  • Import data into a MySQL database from a SQL dump file.

  • Secure the application to prevent public access to application servers and backend systems.

The lab environment and monitoring your budget

This environment is long lived. When the session timer gets to 0:00, the session will end, but any data and resources that you created in the Amazon Web Services (AWS) account will be retained. If you later launch a new session (for example, the next day), you will find that your work is still in the lab environment. Also, at any point before the session timer reaches 0:00, you can choose Start Lab again to extend the lab session time.

Important: Monitor your lab budget in the lab interface. When you have an active lab session, the latest known remaining budget information displays at the top of this screen. This data comes from AWS Budgets, which typically updates every 8–12 hours. Therefore, the remaining budget that you see might not reflect your most recent account activity. If you exceed your lab budget, your lab account will be disabled, and all progress and resources will be lost. Therefore, it’s important for you to manage your spending.

The following are a few suggestions to avoid overspending:

  • Launch only the number of EC2 instances that you need, sized to your requirements.

  • Delete resources and data that you no longer need.

  • Typically, it is compute-type resources, such as Amazon Elastic Compute Cloud (Amazon EC2) instances, Amazon Relational Database Service (Amazon RDS) database instances, AWS Cloud9, and NAT gateway instances, that you leave running that most quickly use up your budget. Turn these off when you no longer need them, or–better yet–delete them.

  • Stop any NAT gateways, EC2 instances, and Amazon RDS instances when they are not in use.

    • Be aware that if you do stop an Amazon RDS instance or cluster and leave it stopped for 7 days, AWS might start it again automatically, which will increase the cost impact.

    • NAT gateway resources, if left running, will also use up your budget.

  • To estimate your costs, use the AWS Pricing Calculator.

Assumptions

This project will be built in a controlled lab environment that has restrictions on services, features, and budget. Consider the following assumptions for the project:

  • The application is deployed in one AWS Region (the solution does not need to be multi-Regional).

  • The website does not need to be available over HTTPS or a custom domain.

  • The solution is deployed on Amazon Linux 2023 machines by using the PHP code that is provided. A template is already available in the lab to launch EC2 instances.

  • The solution uses the PHP code as provided unless the instructions specifically direct you to change the code.

  • The solution uses services and features within the restrictions of the lab environment.

  • The solution uses all the three pairs of subnets provisioned.

  • The solution uses the available AWS Identity and Access Management (IAM) role.

  • The database can be hosted in a single Availability Zone or multiple Availability Zones.

  • Store database connection information in Secrets Manager.

  • The website is publicly accessible without authentication.

Disclaimer: A security best practice is to allow access to the website through authentication. However, because you are building this application as a part of the course, those features are beyond the scope of this project.

Assignment: High-Availability 3-Tier Web Application Deployment on AWS

Course Information

Module: Cloud Infrastructure and Services
Assignment Type: Practical Lab Assessment
Duration: 3-4 weeks
Weight: 30% of final grade
Environment: AWS Learner Lab

Learning Objectives

Upon completion of this assignment, students will be able to:

  1. Design and implement a fault-tolerant, highly available cloud architecture
  2. Deploy a multi-tier application across multiple Availability Zones
  3. Configure load balancers for traffic distribution and failover
  4. Implement secure network access using bastion hosts and security groups
  5. Configure database replication for high availability
  6. Apply AWS best practices for security, scalability, and resilience
  7. Document cloud infrastructure and troubleshoot deployment issues

Assignment Overview

You are required to deploy a 3-tier Task Manager web application to AWS Learner Lab with enterprise-grade availability, fault tolerance, and security. The application consists of:

  • Frontend Tier: React single-page application
  • Backend Tier: Spring Boot REST API
  • Database Tier: MySQL relational database

Your deployment must demonstrate understanding of high-availability architecture patterns, disaster recovery principles, and AWS security best practices.

Technical Requirements

1. Network Architecture (25 points)

VPC Configuration

  • Create a custom VPC with CIDR block (e.g., 10.0.0.0/16)
  • Deploy across at least 2 Availability Zones (AZs)
  • Implement proper subnet segmentation:

Public Subnets (2+ subnets, one per AZ): - Bastion host subnet - Application Load Balancer subnet - NAT Gateway subnet

Private Subnets (4+ subnets, one per AZ): - Backend application tier (EC2 instances) - Database tier (RDS instances)

Internet Connectivity

  • Internet Gateway for public subnet access
  • NAT Gateway in each AZ for private subnet outbound traffic
  • Proper route table configuration for all subnets

Deliverable: Network architecture diagram showing all subnets, AZs, gateways, and routing

2. Frontend Tier - Static Web Hosting (15 points)

Primary Hosting

  • Deploy React application to Amazon S3
  • Enable static website hosting
  • Configure S3 bucket policies for public read access

Content Delivery & High Availability

  • Create CloudFront distribution pointing to S3 bucket
  • Configure CloudFront with:
    • Custom error pages
    • HTTPS support (CloudFront default certificate acceptable)
    • Caching policies for optimal performance
    • Multiple origin support (optional: S3 bucket replication)

Deliverable: Publicly accessible CloudFront URL serving the application

3. Backend Tier - Application Servers (25 points)

EC2 Instance Configuration

  • Deploy minimum 2 EC2 instances running Spring Boot application
  • Instances must be in different Availability Zones
  • Use Auto Scaling Group (ASG) with:
    • Minimum capacity: 2 instances
    • Maximum capacity: 4 instances
    • Desired capacity: 2 instances
    • Health checks enabled (ELB health check type)
    • Launch template or configuration

Application Load Balancer (ALB)

  • Create an Application Load Balancer in public subnets
  • Configure:
    • Target Group with backend instances registered
    • Health check path: /api/tasks
    • Cross-zone load balancing enabled
    • Listener on port 80 (HTTP)
    • Sticky sessions (optional)

Auto Scaling Policies (Optional Bonus: +5 points)

  • Create scaling policies based on:
    • CPU utilization (e.g., scale out at >70%)
    • Request count per target
    • Custom metrics

Deliverable: ALB DNS name with functional API endpoints

4. Database Tier - RDS MySQL (20 points)

RDS Configuration

  • Deploy Amazon RDS MySQL instance with:
    • Multi-AZ deployment enabled (automatic failover)
    • Instance class: db.t3.micro or larger
    • Storage: 20GB minimum, with auto-scaling enabled
    • Automated backups enabled (retention: 7 days)
    • Encryption at rest enabled

High Availability Features

  • Multi-AZ deployment with synchronous replication
  • Automatic failover to standby instance
  • Read replica in different AZ (optional bonus: +5 points)

Database Configuration

  • Create database taskdb
  • Configure security group for MySQL port 3306
  • Allow inbound traffic only from backend security group
  • Configure connection pooling in Spring Boot application

Deliverable: RDS endpoint accessible from backend instances only

5. Security Implementation (25 points)

Bastion Host Architecture

  • Deploy bastion host (jump server) in public subnet
  • Use t2.micro instance with Amazon Linux 2023 or Ubuntu
  • Configure security group:
    • Inbound: SSH (port 22) from your IP only
    • Outbound: SSH to private subnet instances

SSH Access Pattern

  • Backend EC2 instances must be in private subnets only
  • SSH access to backend instances only through bastion host
  • Implement SSH agent forwarding or key distribution
  • Document SSH connection procedure

Security Groups

Create and configure security groups for:

Bastion Host SG: - Inbound: SSH (22) from your IP - Outbound: SSH (22) to Backend SG

ALB Security Group: - Inbound: HTTP (80) from 0.0.0.0/0 - Outbound: HTTP (8080) to Backend SG

Backend EC2 Security Group: - Inbound: SSH (22) from Bastion SG - Inbound: HTTP (8080) from ALB SG - Outbound: MySQL (3306) to RDS SG - Outbound: HTTPS (443) for internet access (via NAT)

RDS Security Group: - Inbound: MySQL (3306) from Backend SG only - No outbound rules needed

IAM Roles (Optional Bonus: +5 points)

  • Create IAM role for EC2 instances
  • Attach policies for CloudWatch, SSM, S3 access
  • Use Systems Manager Session Manager as alternative to SSH

Deliverable: Security group configuration document and SSH access demonstration

6. Application Configuration (10 points)

Backend Configuration

Update Spring Boot application.properties:

spring.datasource.url=jdbc:mysql://RDS-ENDPOINT:3306/taskdb
server.port=8080
# Add connection pool configuration
spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.minimum-idle=5

Frontend Configuration

Update React application to use ALB endpoint:

const [apiUrl, setApiUrl] = useState('http://YOUR-ALB-DNS/api');

Health Monitoring

  • Configure ALB health checks
  • Implement application health endpoint (bonus)
  • Set up CloudWatch alarms (bonus: +5 points)

Architecture Requirements Summary

Mandatory Components Checklist

Deliverables

1. Architecture Documentation (30 points)

Submit a technical report (2000-3000 words) including:

a) Architecture Diagram - Comprehensive network diagram showing: - VPC, subnets, and Availability Zones - All EC2 instances, RDS, and load balancers - Security groups and traffic flow - Bastion host access pattern - Use AWS architecture icons (draw.io, Lucidchart, or CloudCraft)

b) Component Description - Detailed explanation of each AWS service used - Justification for architectural decisions - Configuration details for each component

c) High Availability Analysis - Explain how your architecture achieves fault tolerance - Describe failover scenarios: - Backend instance failure - Availability Zone failure - Database primary failure - Recovery Time Objective (RTO) and Recovery Point Objective (RPO)

d) Security Analysis - Network security implementation - Access control mechanisms - Data protection (encryption at rest/in transit) - Compliance with principle of least privilege

e) Scalability Considerations - How architecture handles increased load - Bottlenecks and limitations - Future improvements

2. Configuration Files (10 points)

Submit all configuration files: - Spring Boot application.properties - Security group rules (JSON export or documentation) - Auto Scaling Group configuration - User data scripts (if used) - Any custom scripts created

3. Deployment Guide (15 points)

Create a step-by-step deployment guide including: - Prerequisites and required tools - AWS resource creation sequence - Configuration commands and scripts - Verification steps for each component - Troubleshooting common issues

4. Video Demonstration (15 points)

Record a 10-15 minute video demonstrating:

Functional Requirements: 1. Application access via CloudFront URL 2. CRUD operations (create, read, update, delete tasks) 3. Data persistence verification

High Availability Testing: 4. SSH access through bastion host 5. Stop one backend EC2 instance - application continues functioning 6. Demonstrate ALB distributing traffic to remaining instance 7. Restart stopped instance - show auto-recovery

Security Demonstration: 8. Attempt direct SSH to backend instance (should fail) 9. Successful SSH via bastion host 10. Show security group configurations in AWS console

Optional Bonus Demonstrations (+5 points each): - Trigger auto-scaling event - Simulate RDS failover - Monitor CloudWatch metrics/alarms

5. AWS Console Screenshots (10 points)

Submit screenshots showing: - VPC with all subnets and route tables - EC2 instances running in multiple AZs - Auto Scaling Group configuration - Load Balancer with healthy targets - RDS Multi-AZ deployment status - Security groups configuration - CloudFront distribution - Resource tagging (all resources properly tagged)

Q: Can I use pre-built AMIs for backend?
A: Yes, but document the AMI source and configuration changes made.
