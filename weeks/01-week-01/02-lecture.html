Lecture Notes

Welcome & Introduction

This module delves into advanced cloud architecture design principles, aligning with the AWS Certified Solutions Architect - Associate (SAA-C03) curriculum. Students will gain a comprehensive understanding of how to design and deploy secure, scalable, highly available, fault-tolerant, and cost-effective applications on AWS. Through hands-on labs and real-world case studies, students will develop the practical skills necessary to become proficient AWS cloud architects.

Mr. John Jennings

Welcome to the Module

Welcome to Secure Public Cloud Services! This module is your gateway into the world of professional cloud architecture, built around the AWS Academy Cloud Architecting curriculum and aligned with the AWS Certified Solutions Architect – Associate (SAA-C03) exam blueprint. Over the coming weeks you will move from foundational cloud concepts to designing secure, resilient, high-performing, and cost-optimized systems on Amazon Web Services.

Your lecturer, Mr. John Jennings, is a member of the IT Department with a teaching and research focus spanning Cloud Computing, AR/VR development in Unity, game design, and human factors. This breadth matters: cloud architecture is not just about servers and storage — it is about designing systems that real people and real businesses depend on, and that theme of human-centred, practical design will run throughout the module.

Why Do We Study Cloud Computing?

Cloud computing has become the default operating model for modern IT — organisations of every size now build, scale, and secure their applications on platforms like AWS rather than in on-premises data centres. Understanding how to architect solutions well on these platforms is now a core professional skill, not a niche specialism.

Module Learning Objectives

By the end of this module, you should be able to:

  1. Analyse the main principles of cloud computing and how they are implemented by providers such as AWS.
  2. Define a solution using architectural design principles derived from customer requirements.
  3. Assess various cloud architectures and implementations in order to solve common infrastructure problems.
  4. Implement a cloud-based architecture grounded in well-designed architectural principles.

Indicative Syllabus

The module is organised into five units, each addressing a different lens on cloud architecture:

  • Unit 1 — Public Cloud Architectures: global cloud infrastructure, and the compute, storage, networking, and managed services that form the building blocks of any AWS solution.
  • Unit 2 — Resilient Architectures: high availability and load-balancing strategies that keep systems running through failure.
  • Unit 3 — High-Performing Architectures: architectural design for performance, auto-scaling, automation, decoupling, web-scale media delivery, and content delivery networks (CDNs).
  • Unit 4 — Secure Applications and Architectures: the AWS shared responsibility model, users/groups/roles, IAM, authentication and authorisation, and bastion hosts.
  • Unit 5 — Cost-Optimised Architectures: revisiting high availability and load-balancing through the lens of cost efficiency.

Alignment to the AWS SAA-C03 Certification

This module’s content closely mirrors the skills validated by the AWS Certified Solutions Architect – Associate (SAA-C03) exam. While this is not an exam preparation course, the overlap is substantial and intentional. The exam — and much of this module — validates your ability to:

  • Design solutions using the AWS Well-Architected Framework.
  • Design solutions that incorporate appropriate AWS services to meet current business requirements and anticipate future needs.
  • Design secure, resilient, high-performing, and cost-optimised architectures.
  • Review existing solutions and identify opportunities for improvement.

If you decide to pursue the SAA-C03 certification after this module, you will already have a strong conceptual foundation.

The Café Business Case

To ground abstract architecture concepts in something tangible, the AWS Academy curriculum uses a running case study: Frank and Martha’s café and bakery. Frank and Martha opened the business in retirement, and over the course of the programme, a small cast of characters — staff and AWS consultants — help them use cloud computing to solve real business problems.

  • Frank — co-owner, a retired navy officer who enjoys baking, non-technical.
  • Martha — co-owner, a retired accountant comfortable with spreadsheets, non-technical.
  • Sofía — their daughter, a supply chain manager with some programming skills, future business administration student.
  • Nikhil — an employee with visual design skills and a growing interest in cloud computing.
  • Olivia — an AWS Solutions Architect specialising in databases and networking.
  • Faythe — a developer skilled in AWS APIs and cloud security.
  • Mateo — a systems administrator focused on automation, repeatable solutions, backups, and disaster recovery.

What makes this case study valuable is that the café’s technical architecture evolves over seven versions, each reflecting a realistic business trigger:

  • V1: A simple static website hosted on Amazon S3.
  • V2: Dynamic content and online ordering — a web application plus a database running on EC2.
  • V3: Web and database layers are separated; the database migrates to Amazon RDS in a private subnet.
  • V4: A Virtual Private Cloud (VPC) is introduced to create secure, isolated subnets.
  • V5: A load balancer, auto scaling, and multi-AZ deployment are added to handle high traffic and improve availability.
  • V6: AWS CloudFormation templates automate deployment across multiple regions.
  • V7: AWS Lambda functions connect to RDS to generate scheduled reports.

You’ll see this business case referenced repeatedly throughout the module — treat it as a running example of how “good enough for now” architecture matures into something genuinely well-architected.

Roles in Cloud Computing

Cloud projects involve several overlapping but distinct roles, and understanding them helps you see where a “cloud architect” fits into a wider team:

  • IT Professional — a generalist who may manage applications and production environments, often highly technical and sometimes specialised (e.g. security, storage). Typical titles: IT administrator, systems administrator, network administrator.
  • IT Leader — leads IT teams, manages operations and budgets, and chooses technologies for the organisation. Often hands-on early in their career before moving into delegation. Typical titles: IT manager, IT director, IT supervisor.
  • Developer — writes, tests, and fixes code, working at the application level using APIs and SDKs, sometimes specialising in areas like security or storage. Typical titles: software developer, system architect, software development manager.
  • DevOps Engineer — builds infrastructure following cloud architect guidelines and continually improves deployment pipelines. Typical titles: DevOps engineer, build engineer, reliability engineer.
  • Cloud Architect — stays current with the technology landscape, helps select appropriate technologies, and provides documentation, processes, and tooling. The cloud architect enables developer innovation and resolves cross-cutting challenges around cost, performance, reliability, and security. Typical titles: cloud architect, systems engineer, systems analyst.

Introducing Cloud Architecting

Taking the perspective of a cloud architect means understanding the practice of applying cloud best practices to a solution that uses cloud services and features to meet an organisation’s technical needs and business use cases. A cloud architect needs to evaluate architectures against the AWS Well-Architected Framework and apply best practices when building solutions on AWS — always working backward from the business need to the architecture, not the other way around.

The role of a cloud architect can be broken into three broad activities:

  • Plan — set technical cloud strategy together with business leads, and analyse solutions against business needs and requirements.
  • Research — investigate cloud service specifications and workload requirements, review existing workload architectures, and design prototype solutions.
  • Build — design the transformation roadmap, including milestones, work streams, and owners, and manage the adoption and migration process.

Key takeaways: Cloud architecture is the practice of applying cloud characteristics to a solution that uses cloud services and features to meet an organisation’s technical needs and business use cases. AWS services allow you to create highly available, scalable, and reliable architectures, and cloud architects are ultimately responsible for managing an organisation’s cloud computing architecture.

The AWS Well-Architected Framework

The AWS Well-Architected Framework is a guide that provides a consistent approach for evaluating cloud architectures and for implementing sound designs. It documents a set of foundational questions and best practices, developed by AWS after reviewing thousands of real customer architectures, organised into six pillars:

Operational Excellence

Run and monitor systems that deliver business value, continually improve supporting processes and procedures, and treat your entire workload — applications, infrastructure, policies, governance, and operations — as code. Treating operations as code lets you apply the same engineering discipline to your infrastructure that you apply to application code, maximising productivity and minimising error rates.

Security

Implement a strong identity foundation, maintain traceability of activity, apply security at every layer (not just the perimeter), and implement risk assessment and mitigation strategies. Protecting data in transit and at rest, and preparing for security events before they happen, are central to this pillar.

Reliability

Design systems that recover quickly from infrastructure or service disruptions, that dynamically acquire compute resources to meet demand, and that mitigate disruptions such as misconfigurations or transient network issues. This pillar directly addresses classic reliability problems: single points of failure, lack of automation, and lack of elasticity.

Performance Efficiency

Choose and maintain efficient resources, and maintain that efficiency as demand changes. “Democratise” advanced technologies by using managed vendor solutions where implementing something yourself would be prohibitively complex. Employ mechanical sympathy — use technologies with an understanding of how they actually operate, for example choosing a database or storage approach based on real data access patterns rather than familiarity.

Cost Optimization

Measure efficiency continuously, eliminate unneeded expense, and adopt the consumption model that fits your usage pattern — often paying only for what you use. Favour managed services where they can operate at cloud scale and offer a lower cost per transaction than a self-managed equivalent.

Sustainability

Establish sustainability goals, maximise utilisation of provisioned resources, choose efficient hardware and software, and reduce the downstream environmental impact of your workloads. This is a continuous effort focused on energy reduction and efficiency across every component of a workload — from programming language choice to right-sized infrastructure.

The AWS Well-Architected (WA) Tool

The AWS WA Tool is a free, self-service tool available in the AWS Management Console that reviews the state of your workloads against the latest AWS architectural best practices. You answer a structured set of questions across the pillars, and the tool delivers an action plan with step-by-step guidance for improvement. It gives you consistent, repeatable access to the same knowledge and best practices used by AWS’s own architects, helping you minimise failures and operational costs, dig into infrastructure and business processes, and feed architecture considerations into your organisation’s governance process.

Key takeaways: The Well-Architected Framework provides a consistent approach to evaluating cloud architectures and guidance for implementing designs, organised into six pillars, each with foundational questions to assess alignment with best practice. The AWS WA Tool operationalises this framework directly in the console.

Best Practices for Building Solutions on AWS

Beyond the Framework’s pillars, AWS Academy highlights a set of concrete, recurring best practices you’ll apply throughout this module:

Design trade-offs. Every architectural decision involves trade-offs — for example, trading consistency, durability, or storage space for lower latency and higher performance, or prioritising speed to market over cost for a new feature. Base these decisions on empirical data (load testing, benchmarking) rather than intuition, since trade-offs can add cost and complexity.

Implement scalability. Design every layer of your infrastructure to handle changes in demand. Tools like Amazon CloudWatch can detect when load crosses a defined threshold (e.g. sustained CPU utilisation) and trigger Amazon EC2 Auto Scaling to launch new instances automatically — and scale back down when demand drops, so you’re not paying for idle capacity. This is far faster and more reliable than manual, reactive scaling.

Automate your environment. AWS provides monitoring and automation tools at virtually every layer. CloudWatch and EC2 Auto Scaling can detect unhealthy resources and automatically launch replacements, notify administrators, and log changes for tracking — removing the need for manual detection and intervention when something fails.

Use Infrastructure as Code (IaC). Provisioning infrastructure through code instead of manual processes lets you rapidly deploy identical environments, dramatically reduce configuration errors introduced by manual steps, and propagate changes consistently across every stack. IaC also makes it straightforward to roll back to a last-known-good configuration if something goes wrong.

Treat resources as disposable. Think of your infrastructure as software, not hardware. Automate the deployment of new resources with identical configurations, stop resources that are not in use, and test updates on new resources before replacing the old ones — this makes it far easier to respond to changing capacity needs and to upgrade safely.

Use loosely coupled components. Traditional architectures often chain tightly integrated servers together, so a failure in one component can cascade and cause the whole system to fail, and scaling requires reconfiguring every connected layer. Loose coupling uses managed intermediaries — load balancers and message queues — between layers, so the intermediary absorbs failures and scaling events automatically. If one application server fails behind a load balancer, traffic simply continues to be routed to the healthy servers.

Design services, not servers. EC2 offers great flexibility, but it shouldn’t automatically be your default choice for everything. Consider containers or serverless solutions where appropriate. Use message queues for inter-application communication, store static assets off-server in Amazon S3, and let managed services like AWS Lambda, Amazon SQS, Amazon DynamoDB, ELB, Amazon SES, or Amazon Cognito handle authentication and state rather than building it yourself.

Choose the right database solution. Match the technology to the workload rather than forcing a workload to fit a familiar technology. Consider read/write patterns, total storage requirements, typical object size and access pattern, durability and latency requirements, maximum concurrent users, the nature of your queries, and how strong your integrity controls need to be.

Avoid single points of failure (SPOFs). Assume everything will eventually fail, and design backward from that assumption. A single database server shared by multiple application servers is a classic SPOF — if it goes down, everything above it goes down too. A common mitigation is a standby replica that can take over automatically if the primary fails, which also reflects the “disposable resources” principle in action.

Optimise for cost. Continually ask whether your resources are the right size and type for the job, which metrics you should be monitoring, how to turn off unused resources, how frequently a resource is actually needed, and whether a managed service could replace a self-managed server. Cloud computing lets you trade fixed expense (hardware you own regardless of use) for variable expense (paying only for what you consume).

Use caching. Caching temporarily stores data in an intermediary location between the requester and permanent storage, reducing both latency and cost for repeated requests. A classic example is Amazon CloudFront placed in front of Amazon S3: the first request fetches from S3 and CloudFront caches a copy at a nearby edge location; every subsequent request is served from that edge location at lower latency and lower cost.

Secure your entire infrastructure. Security must be built into every layer, not just the outer perimeter. Use managed services, log access to resources, isolate parts of your infrastructure from each other (for example using EC2 security groups to limit blast radius), encrypt data in transit and at rest, enforce least-privilege access control, require multi-factor authentication (MFA), and automate deployments so security configuration stays consistent over time.

AWS Global Infrastructure

The AWS Global Infrastructure underpins everything above: it spans over 100 Availability Zones across more than 30 geographic Regions, offering 200+ services from data centres around the world, so you can build highly available, scalable architectures physically close to your customers for lower latency.

Selecting Regions. A Region is a physical geographical area containing two or more Availability Zones, connected to the rest of AWS via a private global backbone network rather than the public internet. Regions are isolated from one another for fault tolerance — data is never automatically replicated across Regions; you are responsible for enabling and controlling any cross-Region replication your business needs require. Some newer Regions are disabled by default and must be explicitly enabled, and isolated Regions such as AWS GovCloud (US) exist to meet specific government regulatory requirements. Region choice should be driven by compliance obligations and network latency requirements.

Selecting Availability Zones. An Availability Zone (AZ) consists of one or more physically separate data centres, designed as an independent failure zone with its own power, cooling, and networking, and interconnected to other AZs in the same Region via high-speed private links. Because no data centre belongs to more than one AZ, and AZs sit in different flood risk zones and power grids, replicating across AZs is one of the most effective ways to build resiliency into a system that must survive a full AZ outage.

Using Local Zones. Local Zones extend a Region into places where no full Region exists, placing compute, storage, database, and other select services physically closer to large population or industry centres. They enable single-digit-millisecond latency for use cases like media production, real-time gaming, and machine learning, while still connecting back to the parent Region over a high-bandwidth, secure link and through the same APIs you already use.

The role of AWS data centres. Data centres are where data physically resides and processing actually happens — typically tens of thousands of servers per facility, all online and actively serving customers. AWS runs core applications in an N+1 configuration so that, in the rare event of a data centre failure, remaining capacity can absorb the load through automated failover. AWS also uses custom network equipment sourced from multiple original device manufacturers (ODMs) with a customised protocol stack.

AWS Points of Presence (PoPs). Edge locations are AWS facilities placed close to customers specifically to deliver content — via services like Amazon CloudFront, Route 53, and AWS Global Accelerator — with the lowest possible latency. Regional edge caches sit between the origin server and the edge locations, holding content that isn’t popular enough to justify a permanent place at the edge, further reducing latency and load on the origin.

Key takeaways: The AWS Global Infrastructure consists of Regions, Availability Zones, and edge locations. Region choice is typically driven by compliance and latency; each AZ is physically isolated with redundant power, networking, and connectivity; and edge locations plus regional edge caches improve performance by caching content close to users.
